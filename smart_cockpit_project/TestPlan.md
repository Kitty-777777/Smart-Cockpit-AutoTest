# 智能座舱蓝牙音乐自动化测试计划

## 1. 项目目标

在虚拟 CAN 总线（python-can）上验证手机与车机的蓝牙音乐相关功能，并核对对应的 CAN 信号状态。车机界面操作后续由 Appium / ADB 接入，本阶段先把测试范围、策略和用例优先级定下来。

核心验证场景：

- 手机与车机蓝牙连接
- 音乐播放 / 暂停
- 来电打断

每条场景同时检查两件事：车机侧功能是否正确，总线上的媒体状态、音量等信号是否与界面一致。

## 2. 测试范围

| 范围 | 包含 | 不包含 |
|------|------|--------|
| 蓝牙配对 / 连接 | 配对、连接成功、已配对设备回连 | 蓝牙协议栈底层兼容性认证 |
| 音乐控制 | 播放、暂停、上一首 / 下一首 | 音源商店、账号登录、在线曲库 |
| 蓝牙通话 | 来电提醒、接听前的媒体让路 | 通话音质、通讯录同步 |

## 3. 测试策略

### 3.1 功能测试

验证 UI 交互和业务逻辑。后续用 Appium / ADB 操作车机：发起连接、点击播放 / 暂停 / 切歌、模拟来电。断言车机当前音源、播放状态和界面提示与预期一致。

### 3.2 总线测试

用 python-can 在虚拟通道 `practice_vcan` 上监听和模拟座舱相关报文。功能动作发生后，检查媒体状态、音量等信号是否同步变化。播放状态约定：`MediaStatus = 0` 表示停止，`MediaStatus = 1` 表示播放。

现有 `bus_util.py`、`ecu_sim.py` 提供虚拟总线和 ECU 仿真，座舱报文在此基础上扩展，不改动原有发动机和诊断练习报文的含义。

### 3.3 异常测试

覆盖连接和播放被打断的路径：

- 播放过程中蓝牙断开
- 来电打断正在播放的音乐，挂断或拒接后的恢复
- 第二台设备抢占当前蓝牙连接

异常路径同时检查界面状态和 CAN 信号，避免只看到界面暂停、总线上仍报播放。

| 项 | 内容 |
|----|------|

## 5. 测试用例分类

先列大纲，不在本阶段写自动化代码。

### P0 核心主流程

- 蓝牙连接成功，车机显示已连接设备
- 连接后播放音乐成功，界面进入播放态
- 来电时音乐自动暂停

### P1 异常与边界

- 播放中蓝牙断开，音乐停止且界面提示断开
- 播放中切换音源，原蓝牙音乐退出播放
- 连续多次切歌，当前曲目与播放状态保持正确

### P2 总线信号

- 播放时 `MediaStatus = 1`
- 暂停或停止时 `MediaStatus = 0`
- 来电打断后，媒体状态从 1 变为 0，与界面暂停一致

## 6. 风险与应对

虚拟环境无法完全模拟真实车载硬件的时序延迟。报文和界面状态可能不是同一时刻就绪。

应对：断言前用有限次轮询或 `time.sleep` 做初步等待，把超时写进用例而不是无限等待。接入实车或台架后，再把固定延时收成对信号变化的等待。

## 7. 交付与目录

座舱测试放在 `smart_cockpit_project/`：

- `TestPlan.md`：本测试计划
- `bus_util.py`：虚拟 CAN 与单帧诊断工具
- `ecu_sim.py`：ECU 仿真

后续用例按 P0、P1、P2 的顺序补到该目录，用 pytest 执行。
